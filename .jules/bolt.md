# Bolt's Journal

## 2026-10-31 - Lazy Set caching for static lookup arrays in Google Apps Script
**Learning:** Google Apps Script scripts often define large lookup arrays at top level (e.g., `tzids` with 589 timezone entries in `tzid.gs`). Repeated `Array.prototype.indexOf` lookups inside per-event loops create significant O(N * M) overhead. Converting arrays directly at global scope to `Set` can break tests or external expectations that treat `tzids` as an Array, but lazily initializing a `Set` (`tzidsSet = new Set(tzids)`) maintains complete backwards compatibility while achieving O(1) lookups (~12x speedup).
**Action:** When optimizing static array lookups in Google Apps Script without changing the public contract or file structure, use a lazily-initialized `Set` variable.

## 2026-11-01 - O(1) Set membership for per-calendar MD5 hash lookups in createEvent
**Learning:** During calendar synchronization in GAS-ICS-Sync, `createEvent` checks whether each incoming ICS event is unchanged by calculating its MD5 digest and scanning `calendarEventsMD5s` using `Array.prototype.indexOf`. For calendars with thousands of existing and incoming events (e.g., max 2500 events per page), this results in an O(N * M) linear scan overhead on every sync iteration. By lazily initializing a `calendarEventsMD5Set` (reset per calendar in `syncCalendar`), lookup complexity drops from O(N * M) to O(N + M) (~40x-80x faster lookup), preventing execution timeouts within Google Apps Script's strict 6-minute execution limit while preserving backward compatibility for unit tests and caller code accessing `calendarEventsMD5s`.
**Action:** Whenever verifying event digests or fingerprints against an existing collection inside an event loop, lazily index the fingerprint list in a Set reset per calendar.

## 2026-11-03 - Hoisting filter-invariant allocations outside per-event predicate callbacks
**Learning:** In Google Apps Script feeds with thousands of events, filtering arrays via `events.filter(...)` with loop-invariant object allocations inside the predicate (such as parsing `new ICAL.Time.fromJSDate(...)` or instantiating `new RegExp(...)` on every item) incurs severe GC and runtime overhead. For 2,500 events across active filters, recomputing `referenceDate` or `RegExp` per item consumes ~40%-80% unnecessary CPU time. Hoisting these calculations outside `events.filter` preserves identical filtering semantics while cutting per-filter execution time dramatically.
**Action:** In collection filtering loops, always hoist invariant date/time calculations and RegExp compilation before the filter iteration.

## 2026-11-05 - O(1) Map grouping in condenseCalendarMap for multi-feed & batch syncs
**Learning:** `condenseCalendarMap` in `Helpers.gs` groups source mapping rows or sync summary events (`addedEvents`, `modifiedEvents`, `removedEvents` in `sendSummary`) by target calendar name. The legacy implementation linearly scanned the accumulator array for matching targets on every item (`O(N * K)`). When processing thousands of events across multiple targets, this nested scan caused noticeable latency and redundant array allocations. Using an auxiliary `Map` to track existing target arrays achieves $O(N)$ linear time grouping (~6.5x to 11x faster) while maintaining exact output array layout and deterministic calendar ordering.
**Action:** When grouping collections by key where the output format requires nested array tuples `[key, [items...]]`, use a `Map` pointing directly to the target item arrays rather than scanning the accumulator array.

## 2026-11-06 - Deferring high-level domain wrapper allocation until cache/digest validation
**Learning:** In recurring synchronizations, 99%+ of incoming items are unchanged. Eagerly instantiating heavy wrapper domain models (such as `new ICAL.Event(event)`) before computing cryptographic digests or cache keys causes enormous throwaway allocation and parsing overhead. Because `ICAL.Event.prototype.toString` delegates directly to the underlying `event.toString()` (`ICAL.Component`), hashing `event.toString()` produces the exact same MD5 digest without allocating `ICAL.Event`. Deferring `new ICAL.Event(event)` until after the unchanged check eliminates ~700ms of CPU time across 2,500 events (~15x speedup: ~750ms -> ~50ms) and avoids thousands of garbage collection cycles.
**Action:** Always compute cache keys or change-detection digests directly on raw components before wrapping them in high-level domain objects, deferring wrapper instantiation until change or creation is confirmed.

## 2026-11-07 - Reusing pre-parsed ICAL.Time objects during event date filtering
**Learning:** In ical.js, `event.getFirstPropertyValue(parameter)` on date-time properties (`dtstart`, `dtend`) already returns an instantiated, parsed `ICAL.Time` object. In `filterResults`, calling `new ICAL.Time.fromString(event.getFirstPropertyValue(filter.parameter).toString(), ...)` forced each date property to format into a string and undergo complete re-parsing through `ICAL.Time.fromString` on every event. For 5,000 events, this redundant stringification and re-parsing consumed ~170ms; reusing the already-parsed `ICAL.Time` directly when `.compare` is available drops execution time to ~7ms (~25x speedup) and avoids allocating thousands of throwaway date strings and parser objects.
**Action:** When working with ical.js component properties, check if `getFirstPropertyValue` already returned a domain object (`ICAL.Time`, etc.) before calling parser constructors like `fromString`.
