# Sentinel's Journal

## 2026-11-09 - Attendee Identity Leak and Unintended Calendar Invites During Title Redaction
**Vulnerability:** In `Helpers.gs`, when users enabled privacy placeholders (`wipeTitles`) to redact sensitive event details before syncing private/work calendars into shared or public Google Calendars, `createEvent` still extracted `ATTENDEE` entries when `addAttendees` was enabled and attached `newEvent.attendees`. `applyPrivacySettings` did not strip `newEvent.attendees`, leaking sensitive participant names and email addresses on destination calendars and inadvertently adding the synced events to attendees' personal calendars.
**Learning:** Privacy redaction models that wipe event summaries to obscure sensitive events must also sanitize attendee participation structures (`newEvent.attendees`) to prevent participant deanonymization and unwanted external event invitations.
**Prevention:** In `applyPrivacySettings`, delete `newEvent.attendees` whenever `wipeTitles` is active.

## 2026-11-07 - Event Organizer Identity and Email Privacy Leak During Title Redaction
**Vulnerability:** In `Helpers.gs`, when users enabled privacy redaction (`wipeTitles`) to replace sensitive event details with generic placeholders before syncing into shared or public Google Calendars, `createEvent` still extracted `ORGANIZER` properties (`cn` and `mailto`) and attached `newEvent.organizer`. While organizer title prefixing was suppressed, the `organizer` object itself was persisted to Google Calendar, exposing confidential organizer names and email addresses on shared or public destination calendars.
**Learning:** Privacy placeholders must scrub both visible text representations (such as title prefixes) and structural event metadata (`newEvent.organizer`) that can expose attendee or organizer identities to unauthorized viewers of target calendars.
**Prevention:** In `applyPrivacySettings`, delete `newEvent.organizer` whenever `wipeTitles` is active.

## 2026-11-06 - Event Source URL Privacy Leak During Description Redaction
**Vulnerability:** In `Helpers.gs`, when users enabled privacy redaction (`wipeDescriptions`) to sanitize event details before syncing into shared or public Google Calendars, `createEvent` extracted the event's `URL` property and set `newEvent.source.url`. `applyPrivacySettings` cleared `newEvent.description` but left `newEvent.source` untouched, leaking confidential URLs (containing private meeting links, internal document paths, or sensitive access tokens) to anyone with access to the destination calendar.
**Learning:** Privacy redaction must inspect all Google Calendar API event properties that convey descriptive context or link to the event's subject matter (e.g. `newEvent.source`), not just `summary`, `description`, and `location`.
**Prevention:** Ensure that `applyPrivacySettings` cleans up `newEvent.source` whenever `wipeDescriptions` is active.

## 2026-11-05 - CRLF Header Injection in Recipient Email Address
**Vulnerability:** In `Helpers.gs`, recipient email addresses (`email`) configured by users or stored via the settings UI were passed directly to `MailApp.sendEmail` in both `sendSummary` and `checkForUpdate` without sanitizing carriage return (`\r`) or newline (`\n`) characters. If `email` contained CRLF sequences (e.g. `user@example.com\r\nBcc: attacker@example.com`), it permitted email header injection, potentially exfiltrating sensitive calendar execution summaries (containing meeting names, descriptions, locations, and attendee schedules) to unauthorized parties.
**Learning:** Sanitizing subject headers alone is insufficient for email security; recipient addresses (`to`) are also email headers in SMTP/mail services and must be strictly sanitized against CRLF injection and checked for non-empty content after sanitization.
**Prevention:** Always strip `[\r\n]` characters and trim whitespace from recipient email addresses before dispatching messages via `MailApp.sendEmail`.

## 2026-11-04 - CRLF Header Injection in Email Summary Subject
**Vulnerability:** In `Helpers.gs`, `sendSummary` constructed email notification subjects by interpolating `customEmailSubject` directly into the subject string (`${customEmailSubject ? customEmailSubject : "GAS-ICS-Sync Execution Summary"}: ...`) and passing it to `MailApp.sendEmail`. If a user-configured or stored setting contained carriage returns or newline characters (`\r` or `\n`), it allowed email header injection (such as injected Bcc, Cc, or Subject headers).
**Learning:** Email headers constructed from user-configurable strings must be strictly sanitized against CRLF characters even in serverless script environments like Google Apps Script.
**Prevention:** Sanitize user-provided email subject inputs by explicitly stripping `[\r\n]` characters before formatting email headers.

## 2026-11-03 - Organizer and Title Privacy Leak During Title Prefixing
**Vulnerability:** When `wipeTitles` was active, `applyPrivacySettings` set `newEvent.summary = genericTitle`. However, in `createEvent`, `addOrganizerToTitle` prefixed `newEvent.summary` with the organizer name (`organizerName + ": " + newEvent.summary`), and if `addCalToTitle` was also enabled, it further modified `newEvent.summary`. Prior to this fix, if `applyPrivacySettings` only overwrote `summary` with `genericTitle`, the calendar prefix was lost, or if `applyPrivacySettings` was evaluated before organizer prefixing, sensitive organizer identities and original event titles were exposed on public/shared destination calendars despite the user enabling privacy placeholders (`wipeTitles`).
**Learning:** Post-processing privacy transforms must ensure that all sensitive field mutations (such as organizer title prepending) cannot re-expose or override redaction guarantees.
**Prevention:** Centralize summary sanitization in `applyPrivacySettings` so privacy placeholders reliably govern final title construction and prevent upstream or downstream feature flags from leaking event metadata.

## 2026-11-02 - Per-Source Privacy Configuration Silently Dropped During Feed Fetching
**Vulnerability:** In `Helpers.gs`, `fetchSourceCalendars` receives source tuples `[url, colorId, privacy]` but only pushed `[urlContent[0], colorId]` to the result list, silently discarding `source[2]` (`privacy`). When `parseResponses` ran during `syncCalendar`, `itm[2]` was always `undefined`, causing per-source privacy overrides to never be attached to parsed events. If a user configured per-source privacy redaction (`wipeTitles`, `wipeDescriptions`, `wipeLocations`) on sensitive feeds syncing to a shared or public calendar while keeping global wipe settings disabled, sensitive event details from those feeds were published in full plaintext.
**Learning:** Pipeline functions that fetch or transform multi-attribute configurations across intermediate stages must preserve and forward all configuration metadata (e.g., tuple forwarding) to downstream processors.
**Prevention:** Include end-to-end integration tests that verify configuration flags survive every intermediate layer from source mapping to API payload preparation.

## 2026-11-01 - Untrusted ICS Feed Internal Property Injection
**Vulnerability:** External ICS feeds can inject custom properties matching internal script properties (specifically `privacy`, `color`, and `parentCal`). When parsing feeds with ical.js, `getPrivacySettings` checked `event.hasProperty('privacy')` and parsed the JSON payload. If the user had not configured a per-source privacy override, a feed-supplied `PRIVACY:{"wipeTitles":false,...}` was parsed and used instead of the user's global privacy settings (`wipeTitles`, `wipeDescriptions`, `wipeLocations`), exposing sensitive event details to shared/public calendars.
**Learning:** In Google Apps Script and custom parser workflows where in-memory object properties are augmented onto parsed components (synthetic metadata on `ICAL.Component`), untrusted input components must be sanitized by stripping internal/synthetic property keys before applying script-managed properties.
**Prevention:** Always strip internal property namespaces or explicitly remove script-managed properties (`event.removeAllProperties(...)`) immediately after parsing untrusted inputs before setting application metadata.
